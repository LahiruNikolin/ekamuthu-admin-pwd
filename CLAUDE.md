# Admin PWA

Read root AGENTS.md first. This project is an independent Android browser client. No imports from sibling apps, no React Native/Expo dependencies, and no changes to iOS routing or the operator web deployment.

Use `npm run build` (typecheck + production build), `npm test` (session/cache regression checks), and `node tests/browser-smoke.mjs` against `npm run preview -- --port 3002` (mocked API). Keep production backend/deployment configuration separate. README documents scope and rollout limitations. Run `npm run test:parity` against the production preview for mutation coverage.

Use the HTTP-only refresh cookie, sessionStorage access token, one in-flight refresh, and central API client. Never cache private API responses in the worker. New operations must use flexible/range booking and court timezone, and must invalidate relevant React Query keys after success. Keep PARITY.md aligned with implemented actions and distinguish fixture coverage from live staging/device verification. Browser push requires migration 061 and VAPID configuration in the backend; never claim it is deployed from a frontend build.

Android responsiveness is the top priority. Keep route bundles lazy, calendar DOM bounded, searches debounced and cancellable, and avoid continuous animation/blur. Preserve build size budgets. Verify large calendars under CPU slowdown, then use real Android hardware before making performance claims.

Calendar UX: show only the Monday–Sunday weekly overview with all play areas visible. The default weekly view has a sticky time axis, seven day groups with nested play-area columns, and duration-positioned bookings. On narrow screens, keep play-area columns readable and horizontally scroll while retaining the time axis. A seven-day jump bar moves to each day without filtering out courts. Render only visible play-area lanes and time-window booking cards. Keep the compact seven-day count matrix in the Booking totals disclosure. Support all assigned venues with each venue’s timezone. Bound the overview to 12 court rows per page and keep detail lists/timeline windowed. Empty overview cells mean no bookings, not confirmed availability.

Calendar booking clicks open the shared booking details inside a native modal dialog. Keep the underlying calendar mounted so week, filters and scroll survive closing. Direct booking URLs remain supported.

Full screen reuses WeekTimeline directly so its appearance, nested day/play-area headers, day jump bar, fixed time axis, scrolling and booking-dialog behavior match the main calendar. The light calendar fills the available mobile viewport in both orientations. Keep only week navigation, refresh and Exit around it. Browser fullscreen is progressive enhancement; the viewport-filling dialog works when the API is unavailable. Keep the regular calendar mounted underneath.

Empty WeekTimeline cells open /bookings/new with courtId, playAreaId, date and venue-wall-time start/end query parameters. Use 30-minute cells unless the court explicitly disallows half hours, then use 60-minute cells. Render only viewport cells, exclude occupied intervals (cancelled games release time), and never add creation cells for legacy slot-based or historical-only play areas. Native scrolling and the existing pinch suppression prevent gesture clicks; pointer drags over eight pixels are ignored. Fullscreen selection closes the board and exits browser fullscreen when opening the draft. Booking resolves the requested court before initializing fields so a previous venue preference cannot shift the selected times. Prefills survive reload, support end-of-day rollover and remain editable; the server still checks availability on save. Main/fullscreen data loading shares useWeekCalendar and its existing cache key. Unused zoom-button callbacks were removed; the pinch range is unchanged.

Full screen has no court filter, courts-per-screen selector, or court pagination. Include every play area in the selected venue scope; pan horizontally through the nested columns.

The main calendar also has no play-area/court filter. Always include all play areas in the selected venue scope, even when an older link contains playAreaId. Booking links still carry playAreaId for precise detail lookup.

WeekTimeline supports grid-only two-finger pinch zoom (25–200%) (without zoom buttons). Scale lane widths and hourly spacing together, keep the pinch midpoint anchored, preserve native single-finger scrolling, and suppress accidental booking clicks after gestures. Coalesce updates with requestAnimationFrame and retain viewport-only rendering. Do not disable page zoom globally. Zoom preference is stored in sessionStorage after movement settles.

Local HTTPS API proxy uses an IPv4 keep-alive agent because the staging hostname can advertise an unreachable IPv6 route. Keep certificate verification enabled and proxy timeouts bounded. This setting applies to the Vite development proxy, not deployed API clients.

Production builds use Terser with two compression passes and explicit lazy domain chunks (calendar and venue tools). Keep onlyExplicitManualChunks enabled so shared runtime dependencies do not pull the calendar into login. Vite emits a build manifest; the performance gate counts the entry plus transitive static imports for its startup budget. Vercel build settings live in static vercel.json. scripts/build-vercel.mjs emits the Build Output API v3 .vercel/output/config.json and static files after Vite; literal output routes select the API with the deployment PROD variable: true means production, false means staging, and missing means staging. Keep only static vercel.json at the project root; computed destinations in vercel.mjs fail Vercel schema validation. Keep .vercel/output generated and ignored. Set PROD=true on the production Vercel project before deploying this configuration; set false on staging/preview. Preserve same-origin /api/v1 browser URLs and cache exclusions. The explicit PROD flag takes precedence over API_PROXY_TARGET locally; without PROD, local development retains API_PROXY_TARGET/localhost. Reject invalid PROD values or a conflicting direct VITE_API_URL. This flag is separate from Vite's import.meta.env.PROD.

Feature forms use shared Page, Field, Form, Load and EmptyState components for consistent mobile controls, focus, feedback and loading/error states. Booking creation uses separate date/time inputs, venue-time wall-clock duration shortcuts, range review, overlap validation and a sticky save action above navigation. Successful creation returns to the chosen calendar date; never submit live bookings solely for visual QA. Keep booking/calendar code separate from unrelated account/report tools in lazy chunks. Related operator overview screens compress together while remaining lazy.

Session continuity: refresh access tokens before expiry through the persistent HTTP-only cookie, deduplicate refreshes and reuse tokens renewed after a delayed 401. Never sign out on transport/5xx/malformed refresh responses or a resource 401 after successful renewal. Only a rejected refresh session requires login; preserve its return URL. Login itself must attempt silent restoration. The existing backend rotates a 30-day refresh cookie, extending the session on use; clearing browser data, revocation, or 30 days without renewal still requires sign-in. The local Vite HTTP proxy adapts Secure/SameSite=None response cookies only for development; deployed HTTPS cookies stay Secure.

Calendar controls stay minimal: week navigation/date picker, refresh, new booking and fullscreen. No Today/Day/view toggles, cancellation filter, booked/blocked key, zoom buttons or jump-to-hour selector. Keep the seven-day navigation and two-finger pinch. Cancelled games always appear with a dashed red style and explicit status in both normal and fullscreen timelines. Same-area overlapping cancellations and replacement bookings remain separate selectable entries, marked as time rebooked. Cancelled entries do not consume availability or count as active bookings.

Venue choice belongs only on /settings (including sys-admin All venues). Remove global/calendar/report venue switches; the selected venue is a per-user local preference, while authorized booking/notification deep links still select their own venue. Settings remains reachable when All venues is selected. At zoom below 50%, show a compact overview with thin event bars and full accessible booking labels; keep pinch anchoring, bounded rendering, and tap suppression. Booking detail content is shared by direct links and the mobile bottom-sheet dialog: status, time, customer and value first, with contact/release editors in disclosures.

Shared feature pages use a prominent Back to [destination] control. Price template cards use active play-area assignments from template.activations (the backend returns active assignments only) to distinguish Currently active, Partly active paired templates, and Not active. Show assigned areas per weekday/weekend member and sort active templates first; never imply that a template is active venue-wide.

Price template create/edit use standalone /templates/new and /templates/:id/edit pages. New flexible opening ranges accept hourly rates and normalize to the API’s total range price; legacy edits retain existing range-price values. Saving a new template never activates it. Keep weekday/weekend opening-day semantics, overnight offsets, price/overlap validation, and explicit activation. Public legal text is fetched from an immutable Vite asset to avoid parsing static copy as JavaScript; its contents remain unchanged.

Use Price templates for the venue section and Templates/New template/Edit template elsewhere. Activate is disabled while a template has any active assignments (including partly active pairs). Validate ranges before save confirmation: reject duplicates, containment, overnight overlaps and conflicts across recurring opening days, including Friday/Saturday and Sunday/Monday. Adjacent ranges may share a boundary. Activation and edits also check the active opposite day type on affected play areas. Keep opening-day offsets independent of device timezone; these PWA checks supplement backend overlap protection.

Web Push uses a dedicated emerald Sinhala එ notification icon and a white transparent Android status-bar badge under public/icons/notification-*. Keep icon URLs local and fixed in the service worker; notification payloads cannot replace them. The badge is 96px and the card icon is 192px. Editable SVG outlines sit beside the PNG assets, with no runtime font dependency. Icon bytes participate in the worker build hash and icon URLs include that version. The worker activates immediately and claims clients safely because it caches only the public offline document; private/API data and application JS are never cached.

Dashboard puts today’s games before monthly metrics, using reusable game rows and explicit capacity labels (the list API does not return attendance, end times or play-area names). Game details use separate summary, organiser, player roster and management disclosures; retain all status guards and confirmations. Notifications use All updates/Unread tabs and venue-time date groups, preserving deep links and read actions. Account, player directory and reports share the same mobile spacing and accessible touch targets. Route pathname changes scroll to the top; calendar query changes and booking dialogs preserve their existing position. Production targets ES2022 to avoid redundant class-field transforms on modern Android browsers, with startup/total gzip limits unchanged. Games compress with the lazy admin tools; booking creation remains separate from those tools and calendar.

Browser notification state is scoped to the current origin and backend VAPID public key. Do not show an old staging-key subscription as enabled on production. Enabling after a key/environment change unsubscribes the old local endpoint before creating the current-key subscription; register that endpoint with the signed-in admin. A new domain still needs the admin’s browser permission and a new subscription. Production API and worker use their own matching Web Push credentials; staging keys/subscriptions are not copied across environments.

Shared Contact renders the customer/organiser name and phone above two equal-width, 54px Call/WhatsApp links. Keep the existing tel and wa.me destinations, visible text labels and keyboard focus states. Decorative phone/chat masks are lightweight local SVG assets in public/icons/contact-*.svg, without a JavaScript icon dependency. Game organiser actions span the full card width below the avatar/name; booking dialogs and direct detail pages use the same contact component. Hide actions when no callable phone is available.

Notification game links prefer server payload.game_id, with entity_id fallback for AdminGameBooked/Cancelled/NoShow, AdminScheduleChanged, GameCreated, GameCancelled and game.cancelled.schedule_change. Encode the game ID as one route segment. Start read acknowledgement without awaiting it before navigation. Browser push still enters through /notifications?open=<owned notification ID>; replace this intermediate history entry when routing to the game so Back cannot reopen it in a loop. Preserve reservation/calendar targets for non-game alerts and the existing authenticated notification lookup.

Browser notification clicks call clients.openWindow immediately while click activation is available; Chrome Android can reuse the installed PWA. Do not wait for window discovery or a hidden client's navigation before launching/focusing. If opening fails or returns null, try same-origin clients, focusing before navigating, and continue past stale clients or navigation failures. A focus rejection after a successful open must not create a duplicate window. Keep external push URLs ignored and use the authenticated notification-ID route. Real Android launch confirmation remains separate from worker VM tests and provider acceptance.
